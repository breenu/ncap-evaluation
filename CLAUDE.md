# CLAUDE.md — NCAP Evaluation Project

## What this project is

"Weather, Monitors, or Policy? A Meteorologically Normalised, Quasi-Experimental Evaluation of India's National Clean Air Programme, 2015–2025."

The full specification is `docs/proposal.pdf`. **Read it completely before doing anything.** It defines the research questions (RQ1–RQ4), the datasets, the 11-stage methodology, the robustness checks, the figures, the repo layout and the things not to do. Treat it as the spec. Where this file and the proposal disagree, this file wins.

Owner: Reenu, final-year CS student, building this as the main data science project for UK MSc Data Science applications (2027 entry). The project must be something Reenu can explain and defend line by line in an interview, so clarity of reasoning matters as much as the code.

Machine: Windows 11, HP Pavilion 14, Intel i7-1255U (10 cores), 16 GB RAM, ~169 GB free disk, NVIDIA MX550 2 GB (not needed; treat as CPU-only)

## How to work

- Work in phases (below). At the end of every phase: run the tests, commit, update `docs/PROGRESS.md`, write the phase note, then **stop and wait for approval** before starting the next phase.
- Plan before coding. For each phase, first write a short plan of the files and functions you will create, then build.
- Every stage must be scripted and reproducible. `make all` (or `snakemake`) must rebuild every processed file and every figure from `data/raw/`. Nothing the report depends on may live only in a notebook.
- `docs/PROGRESS.md` is the handoff file. Keep it current: what is done, what is next, open problems. A fresh session should be able to continue from it alone.
- `docs/DECISIONS.md` logs every judgement call (thresholds, exclusions, model settings, which data version, anything the proposal left open) with one or two sentences of reasoning. Append, never rewrite.
- After each phase, write `docs/phase-notes/NN-<name>.md`: a plain-language explanation of what was done, why, and what the results show, written for someone who will be questioned on it.

## Hard rules

1. **Never fabricate data or numbers.** If a download fails, a URL has moved, an API has changed, or a dataset does not contain what the proposal expects, stop and tell me. Do not substitute synthetic, simulated or "example" data anywhere in the real pipeline. Synthetic data is allowed only inside `tests/`, clearly labelled.
2. **Verify facts in the proposal before relying on them.** City counts, funding totals, product version names (e.g. ACAG V6.GL.02.04, V5.GL.05.02), coverage years and URLs may be out of date. Check the source and record what you found in `DECISIONS.md`.
3. **Every number in the report is generated by the pipeline.** No hand-typed results in prose, tables or figures.
4. **The pre-registration gate (see Phase 4).** No code that estimates post-2019 NCAP treatment effects may be run until `docs/analysis_plan.md` has been written, approved by me, and committed. Descriptive work and pre-2019 checks are fine before that.
5. **Secrets.** API keys (Copernicus CDS, NASA FIRMS, OpenAQ) go in `.env` or the tool's standard config file, never in code or git. Add them to `.gitignore` before the first commit. When you need a key, ask me for it.
6. **Large downloads.** Before any download over ~2 GB, tell me the estimated size and wait. Never download hourly ERA5 for all of India; request station grid cells only, or use Open-Meteo point queries.
7. **Raw data is immutable.** Everything in `data/raw/` stays exactly as downloaded, with a manifest (source URL, download date, checksum). Raw data is not committed to git.
8. **Report results honestly.** Report robustness checks that weaken the result. Null results are reported with the minimum detectable effect. Never write "NCAP caused X" without its caveats beside it.
9. **Protect the core.** Never cut: the data-quality audit, deweathering, network-composition correction, the satellite synthetic DiD. If time runs short, cut in this order: funding dose-response, ground-station DiD, dashboard, FIRMS fire covariate.

## Out of scope (do not add)

Forecasting models (LSTM/transformers), extra pollutants beyond PM2.5 and PM10 (NO2 only as a secondary check), health or mortality modelling, source apportionment, real-time dashboards or deployed APIs, regression discontinuity on non-attainment status, causal forests or double ML as the headline method, any LLM component, the Kaggle "Air Quality Data in India" dataset.

## Stack

Python for the pipeline: polars or pandas, duckdb, pyarrow, xarray, rioxarray, geopandas, exactextract, ruptures, lightgbm, pygam, pymc or bambi, pysyncon / differences, Snakemake or Make, Quarto, Streamlit. R only where clearly better (`mgcv`, `synthdid`, `did`), called from the pipeline. Pin the environment (`environment.yml` or `uv` lockfile). Unit tests with pytest, especially for every cleaning and flagging rule.

## Phases

**Phase 0 — Plan (no code).** Read the proposal. Write `docs/PLAN.md`: task breakdown per phase, the files you expect to create, data sizes and access requirements for each source, risks, and a list of questions for me. Stop.

**Phase 1 — Skeleton.** Repo layout exactly as in the proposal, environment file, Makefile/Snakefile with stub targets, `config/` YAML for thresholds and parameters, pytest set up, `.gitignore`, `README.md` stub, `docs/PROGRESS.md`, `docs/DECISIONS.md`. Stop.

**Phase 2 — Acquisition.** Idempotent downloaders in `src/acquire/`, one module per source: OpenAQ v3 / CPCB, WashU ACAG NetCDF, ERA5 (targeted cells) or Open-Meteo, NASA FIRMS, GHSL + WorldPop. NCAP city list and funding tables: extract from PDFs with pdfplumber or camelot into CSVs where every row records its source document and page number; check against the totals printed in each document and list every mismatch for me to verify by hand. Write a data card per source in `docs/`. Stop.

**Phase 3 — Storage, cleaning, audit, EDA (RQ1).** Parquet + DuckDB. The station audit exactly as in proposal stage 3 (impossible values, flatlines, changepoints, spatial inconsistency, reliability score, completeness rules with sensitivity, missingness analysis). EDA from stage 4, including the station-entry map. Produce `docs/audit_report.md`. Stop.

**Phase 4 — Analysis plan gate.** Draft `docs/analysis_plan.md` (about 2 pages): estimand, hypotheses, treatment definition, control pool, estimators, robustness checks, decision rules. Stop. I review, edit and may register it on OSF. Only after I approve and it is committed do later phases begin.

**Phase 5 — Deweathering (RQ2).** Grange & Carslaw method, LightGBM and GAM, weather resampling, blocked time-series CV, aggregation to city-month and city-year. Stop.

**Phase 6 — Network-composition correction (RQ1).** All-stations vs balanced panel vs satellite (ACAG over GHSL boundaries). Decomposition figure v1. Stop.

**Phase 7 — Causal analysis (RQ3).** Layer A satellite synthetic DiD + event study + Callaway & Sant'Anna; Layer B ground ITS and DiD; explicit 2020 handling; triangulation. Run every robustness check in the proposal's validation table. Stop.

**Phase 8 — Heterogeneity and mechanism (RQ4).** Bayesian hierarchical model of city effects, moderators, funding dose using allocations, PM10 vs PM2.5 test. Stop.

**Phase 9 — Figures and dashboard.** The eight figures from the visualisation plan with the style rules (units on every axis, uncertainty on every estimate, colour-blind-safe palettes). Read-only precomputed dashboard. Stop.

**Phase 10 — Report and release.** Quarto technical report (20–30 pages), one-page results summary, 2-page policy brief, final README, reproducibility check from a clean clone. Stop.
